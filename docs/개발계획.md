## 1. 이어서 작업할 때 확인할 사항

이 문서를 읽고 현재 파일·Git 상태를 확인한 뒤 아래 단계 1부터 진행한다. 실제 구현 이후에는 단계별 완료 상태와 검증 결과를 이 문서에 갱신한다.

- 최신 결정은 **공개 배포와 Neon을 제외하고 로컬 환경에서 개발하는 것**이다.
- 기능명세서는 이 계획과 동일한 SQLite·로컬 실행 기준으로 갱신했다. 이후 범위·구성 변경 시 두 문서를 함께 갱신한다.
- 문서는 저장소 루트 `docs/`를 기준으로 관리하며, 별도 명세서 사본을 만들어 서로 다르게 유지하지 않는다.
- `docs/`에는 문서관리용 개발계획·개발기록·기능명세서만 둔다. 작업 결과 보고서는 `reports/`, 출처 검토 입력은 `config/`, 검색 평가 입력은 `evals/`에 두며, 자동 생성 도구도 이 구분을 따른다.
- 사용자 안내로 `../streamlit_lab/step6_context.py`의 GMS 주소와 `gpt-5.4-nano` 호출 규격을 확인했다. 실제 키 파일과 임베딩 규격은 미확인이다. 비밀값은 문서나 Git에 저장하지 않는다.
- 사용자가 말한 `5.6 Sol`은 표시 이름이다. 실제 모델 ID·API 주소·요청 형식·임베딩 지원은 확인 전까지 추정하지 않는다.
- 초기 3개 게임은 파이프라인 검증용이다. 최종 목표인 **100개 이상 게임의 규칙 지원**을 대체하지 않는다.

## 2. 목표와 확정 구성

로컬에서 게임 선택 → 규칙 질문·상황 판정 → 근거 확인까지 동작하는 서비스를 완성한다.

| 영역 | 구성 |
|---|---|
| 프론트엔드 | Next.js App Router + TypeScript |
| 백엔드 | Python + FastAPI |
| 일반 DB | SQLite + SQLAlchemy + Alembic |
| 벡터 DB | 로컬 ChromaDB, `game_meta`·`rule_docs` 유지 |
| 원문 저장 | 로컬 폴더의 PDF·추출 텍스트 |
| RAG | LangGraph `retrieve → generate`, 프롬프트 3개 |
| 의존성 관리 | 프론트 pnpm, 백엔드 uv |
| 실행 환경 | Windows 로컬, Docker 없이 실행 |

- Neon·Chroma Cloud·공개 배포·도메인·클라우드 저장소 설정은 제외한다.
- 외부 모델 API와 문서 수집에는 인터넷 연결이 필요하다. 완전 오프라인 서비스는 아니다.
- 필수 F2001~F2012, 비기능 NF2001~NF2007, Next.js 화면 F2013을 구현한다.
- 핵심 심화는 **하이브리드 검색, MMR 비교, RAG 전후 평가, 공식 FAQ 결합**으로 정한다.
- 별도 Reranker, OCR, 퀴즈, 준비 가이드, 계정 로그인은 후속 범위로 남긴다.
- 최종 데이터 목표는 **100개 이상 게임의 메타데이터와 게임별 지원 판본의 공식 규칙 확보·색인·검증**이다.
- 한국어 공식 문서를 우선 사용하되 영문 공식 문서도 허용한다. 한국어로 답변하고 원문 언어·판본을 표시한다.

## 3. 모노레포와 로컬 저장 구조

현재 Git 저장소인 `Rule_U/`를 애플리케이션 모노레포 루트로 사용한다. 계획과 명세서는 현재 실제 위치인 `Rule_U/docs/`에 유지한다.

```text
Rule_U/
├─ docs/                  # 기능명세서·개발계획
├─ apps/
│  ├─ web/                # Next.js
│  └─ api/                # FastAPI, 모델, 마이그레이션, 테스트
├─ tests/e2e/             # 브라우저 검증
├─ data/                  # app.db, chroma/, originals/, extracted/ (Git 제외)
└─ README.md
```

- 실데이터, DB 파일, API 키는 Git에서 제외한다. 출처 목록·설정 예시·재현용 테스트 자료는 관리한다.
- SQLite는 기준 데이터, ChromaDB는 다시 만들 수 있는 검색용 데이터로 관리한다.
- API는 로컬 단일 프로세스로 실행한다. SQLite 쓰기는 짧은 트랜잭션으로 처리하고 외부 API 응답 대기 중에는 트랜잭션을 유지하지 않는다.
- 수집·색인과 질문 작업은 같은 Python 서비스 계층을 사용한다. 별도 Redis·작업 서버는 도입하지 않는다.
- 현재 `docs/`는 `Rule_U/` Git 저장소 안에 있다. 원래 계획의 저장소 외부 경로 설명을 실제 상태에 맞게 정정했으며 파일은 이동하지 않았다.

## 5. API·설정 변경

명세서의 `/api/v1` 계약을 유지한다.

| 기능 | API |
|---|---|
| 게임 목록·상세 | `GET /games`, `GET /games/{game_id}` |
| 자연어 게임 탐색 | `POST /games/search` |
| 대화 생성·조회 | `POST /conversations`, `GET /conversations/{id}` |
| 질문 제출 | `POST /conversations/{id}/messages` |
| 요청 상태·결과 | `GET /requests/{request_id}` |
| 인용 근거 조회 | `GET /sources/{source_id}` |
| 서비스 상태 | `GET /health` |

- 질문 제출은 `202 Accepted`와 요청 ID를 반환한다.
- 동일 `client_request_id` 재전송은 기존 요청을 반환한다. 같은 대화의 다른 요청이 처리 중이면 중복 실행을 막는다.
- 서버 재시작으로 중단된 작업은 실패 상태로 전환해 재시도할 수 있게 한다.
- 로컬 원문은 문서 ID로 조회하고 임의 파일 경로 입력은 허용하지 않는다.
- 수집·색인 CLI는 메타데이터 적재, 문서 수집, 색인, 상태 확인, 평가 실행을 제공한다.
- OpenAPI 기반 TypeScript 타입 생성으로 프론트와 응답 형식을 맞춘다.

주요 설정은 DB URL, 데이터 경로, 모델 API 주소·키·모델 ID, 임베딩 모델, 청킹 크기, Top-k, 검색 모드다. 임베딩 모델이나 차원이 바뀌면 기존 색인을 섞어 쓰지 않고 재생성한다.

초기 검색 설정은 명세서의 청크 1,000자·중복 200자·외부 근거 5개·후보 20개를 사용하고 평가 결과로 조정한다. 수치는 성능 보장값이 아니다.

2026-10-22 사용자 결정: 현재 페이지별 최대 1,000자·중복 200자·줄바꿈 우선 분할과 FAQ 질문/답변 단위 보존을 유지한다. 의미 단위 청킹 보완은 선행 필수 작업으로 두지 않고, 추후 검색·답변 성능 평가에서 개선 필요성이 확인되면 변경하여 기존 방식과 비교한다.
