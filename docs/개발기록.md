## 기록 방법

이 문서는 **왜 요청했고, 무엇을 고민했으며, 어떻게 바뀌었는지**를 기록한다. 기능 요구사항은 기능명세서, 단계별 완료 여부는 개발계획, 설치·실행 명령은 README에서 관리한다.

새 요청이나 결정이 생기면 날짜와 기록 번호를 붙여 아래에 추가한다. 기존 결정을 바꾸는 경우 이전 기록을 지우지 않고 변경한 이유와 대체하는 기록 번호를 남긴다. 실제로 사용자가 말한 내용과 구현 과정에서 개발자가 검토한 내용을 구분한다. 확인되지 않은 의도나 고민을 사용자 발언으로 기록하지 않는다.

API 키, 인증 토큰, 개인정보는 기록하지 않는다. 연결 검증은 설정 예제 확인, 테스트용 응답 검증, 실제 API 호출 성공을 구분한다.

## 초기 세팅 설명

### 현재 개발 상태

2026-10-22 기준으로 1단계의 프로젝트 기반과 로컬 저장 흐름을 구현했다. 게임 선택부터 질문 저장, 테스트 응답 표시, 새로고침 후 대화 복원까지 실행할 수 있다. **실제 모델과 임베딩 API 연결은 미검증이므로 1단계 전체 완료 상태는 아니다.**

현재 데이터는 저장 기능을 확인하는 가상 게임 1개와 테스트 판본이다. 공식 규칙을 확보한 게임은 아니며 실제 보드게임 규칙을 판정하지 않는다. 초기 검증 후보 3개 게임과 최종 목표 100개 이상 게임 지원은 이후 데이터 확보 단계의 범위다.

### 기술 구성과 역할

| 구성 | 역할 | 현재 상태 |
|---|---|---|
| Next.js App Router + TypeScript | 게임 선택·대화 화면과 API 호출 | 기본 화면 구현, Next.js 16.4.2 빌드 검증 |
| Python + FastAPI | 입력 검증, 대화·요청 처리, 저장·조회 API | 구현 |
| SQLite | 게임·문서·대화·요청의 영속 저장 | 로컬 `data/app.db` 사용 |
| SQLAlchemy | Python 객체와 DB 테이블 연결, 트랜잭션 처리 | 모델·제약조건 구현 |
| Alembic | DB 스키마 변경 이력을 코드로 관리 | 초기 마이그레이션 구현·검증 |
| 채팅 연결부 | 모델 제공업체 요청·응답 처리 | mock 및 GMS 예제 규격의 호환 연결부 구현 |
| 임베딩 연결부 | 검색용 벡터 생성과 차원 검증 | mock 및 호환 연결부 구현, 실제 지원 모델 미확인 |
| ChromaDB | 게임 메타데이터·규칙 청크의 벡터 검색 | 후속 구현 예정, 저장 경로만 준비 |
| LangGraph | `retrieve → generate` RAG 흐름 | 후속 구현 예정 |
| pnpm / uv | 프론트엔드 / 백엔드 의존성 관리 | 잠금 파일 포함 |

기존 계획에 따라 Windows에서 Docker 없이 실행한다. 공개 배포, Neon, Chroma Cloud는 현재 범위에 포함하지 않는다. 로컬 실행을 기준으로 하지만 향후 실제 모델 호출과 문서 수집에는 인터넷 연결이 필요하다.

### 디렉터리 구조

```text
Rule_U/
├─ apps/
│  ├─ web/
│  │  ├─ src/app/                # 화면·레이아웃·스타일
│  │  └─ src/lib/api.generated.ts # OpenAPI에서 생성한 타입
│  └─ api/
│     ├─ rule_u/                 # 설정·DB·모델·API·연결부·CLI
│     ├─ migrations/             # Alembic 스키마 변경 이력
│     ├─ tests/                  # 백엔드 검증
│     └─ uv.lock                 # Python 의존성 잠금 파일
├─ tests/e2e/                    # 브라우저 통합 검증
├─ docs/                         # 명세·계획·개발 기록
├─ data/                         # DB·원문·추출문·색인, Git 제외
├─ .env.example                  # 비밀값 없는 설정 예제
├─ pnpm-lock.yaml                # 프론트엔드 의존성 잠금 파일
```

화면과 API를 한 저장소에서 관리하되 `apps/web`과 `apps/api`로 나눈다. 설정 파일은 저장소 루트 `.env`를 읽도록 구성했으며, 실제 키는 사용자가 로컬에서 설정해야 한다. 다른 프로젝트의 `.env`를 자동으로 읽지는 않는다.

### 화면과 API가 연결되는 방식

웹 개발 서버는 `127.0.0.1:3000`, FastAPI는 `127.0.0.1:8000`에서 실행한다. 브라우저는 웹 서버의 `/api/v1` 주소로 요청하고, Next.js가 해당 요청을 FastAPI로 전달한다. API 문서는 `http://127.0.0.1:8000/docs`에서 확인한다.

현재 질문 처리 흐름은 다음과 같다.

1. 샘플 게임을 선택하면 선택 게임·판본과 익명 세션을 연결한 대화를 생성한다.
2. 질문을 보내면 사용자 메시지와 요청 상태를 SQLite에 저장한다.
3. API는 `202 Accepted`와 요청 ID를 반환한다.
4. 백그라운드 작업이 테스트 응답을 생성하고 응답 메시지와 완료 상태를 저장한다.
5. 웹은 요청 상태를 조회해 완료된 대화를 표시한다.
6. 새로고침하면 브라우저에 보관한 대화 ID와 세션 쿠키를 이용해 SQLite의 대화를 다시 불러온다.

대화 본문은 DB에 저장한다. 브라우저의 localStorage에는 최근 대화 ID를 저장하며, 이것만으로 대화 접근 권한을 부여하지 않는다. 서버에서 세션 쿠키와 대화 소유 세션을 비교하고 다른 세션의 접근을 차단한다.

현재 UI는 샘플 게임의 첫 판본을 사용한다. 전체 판본·확장 선택, 게임별 대화 전환, 실제 인용 근거 패널은 후속 화면 구현 범위다.

### DB와 요청 처리에서 미리 준비한 부분

게임, 판본, 확장, 문서, 문서 적용 범위, 수집 상태, 대화, 메시지, 인용, 요청을 저장하는 10종의 엔터티와 다대다 관계용 연결 테이블 2개를 만들었다.

| 준비한 사항 | 필요한 이유 |
|---|---|
| 게임·판본 일치와 확장 호환 제약 | 다른 게임이나 호환되지 않는 판본의 데이터 연결 방지 |
| 문서와 적용 범위 분리 | 하나의 원문을 여러 게임·판본 범위에 연결 |
| 인용 제목·버전·페이지 등의 스냅샷 | 원문 정보 변경 후에도 과거 답변의 인용 정보 보존 |
| 대화별 `client_request_id` 중복 방지 | 같은 요청 재전송 시 메시지와 작업이 중복 생성되는 문제 방지 |
| 대화당 진행 중 요청 1개 제한 | 같은 대화에서 여러 생성 작업이 겹치는 문제 방지 |
| 시작 시 미완료 요청을 실패로 복구 | 서버 종료로 중단된 요청이 계속 처리 중으로 남는 문제 방지 |
| 외래키 검사·WAL·쓰기 대기 시간 설정 | SQLite 데이터 무결성과 로컬 읽기·쓰기 처리 지원 |

DB는 애플리케이션 실행 시 임의로 테이블을 만드는 방식 대신 `alembic upgrade head`로 준비한다. API는 단일 프로세스로 실행하며, 연결부 응답을 기다리는 동안 DB 트랜잭션을 유지하지 않도록 구성했다.

### 모델과 임베딩 설정

사용자 안내에 따라 `../streamlit_lab/step6_context.py`에서 다음 예제를 확인했다.

| 항목 | 확인한 내용 |
|---|---|
| 제공 경로 | GMS |
| API 기본 주소 | `https://gms.ssafy.io/gmsapi/api.openai.com/v1/` |
| 예제 모델 ID | `gpt-5.4-nano` |
| 인증 설정 | `GMS_KEY`를 API 키로 전달 |
| 호출 형태 | `chat/completions` 호환, `model`과 역할별 `messages` 전달 |

기존 계획의 `5.6 Sol` 표시 이름과 예제의 실제 모델 ID가 동일하다고 판단하지 않았다. 현재 기본 모델 ID는 확인 가능한 예제 값을 사용했으며 실제 호출 성공을 뜻하지 않는다.

채팅과 임베딩은 주소·키·모델을 각각 설정할 수 있게 분리했다. 채팅 모델이 응답한다고 해서 임베딩 지원까지 확인된 것으로 처리하지 않기 위해서다. 임베딩 응답은 개수, 인덱스, 숫자 유효성, 차원을 별도로 검사한다.

기본 설정은 두 연결 모두 `mock`이다. mock 채팅은 규칙 판정 불가를 명시한 테스트 문구를 반환한다. mock 임베딩의 8차원 벡터는 연결 구조를 확인하는 테스트 데이터이며 의미 검색용 모델 결과가 아니다.

`probe --live`는 mock 결과를 실제 연결 성공으로 인정하지 않는다. 실제 키와 임베딩 모델 정보가 없으므로 현재 결과는 두 연결 모두 `not_verified`다. 실제 채팅 호출은 probe에서 검증하도록 마련했고, 웹 질문 흐름은 공식 규칙 검색을 연결하기 전까지 mock 전용이다.

설정 방법과 실행 명령은 [README의 실제 연결 검증 안내](../README.md#설정과-실제-연결-검증)를 따른다.

## 요청·고민·변경 이력

### 기록 001 — 기존 개발 방향 정리

- 기록일: 2026-10-22
- 근거: 기존 기능명세서와 개발계획. 아래는 문서에 남아 있는 결정의 요약이며, 과거 사용자 발언을 새로 복원한 것이 아니다.
- 요청·목표: 보드게임 선택 → 규칙 질문·상황 판정 → 공식 근거 확인이 가능한 서비스를 로컬에서 개발한다.
- 문서에 반영된 검토 사항: 로컬 개발과 공개 배포의 범위, 일반 DB와 벡터 DB의 역할, 초기 검증 규모와 최종 지원 게임 수, 필수 기능과 심화·후속 기능의 구분.
- 확정 방향: SQLite와 로컬 ChromaDB를 사용하고 공개 배포·Neon은 제외한다. 초기 3개 게임 검증 후 100개 이상 게임 지원으로 확장한다. 하이브리드 검색·MMR 비교·RAG 전후 평가·공식 FAQ 결합을 핵심 심화로 둔다.
- 남은 사항: 실제 공식 문서 확보와 색인, 근거 기반 답변, 평가와 지원 게임 확장.

### 기록 005 — 로컬 검증 중 발견한 문제 수정

- 날짜: 2026-10-22
- 발견 및 수정:
  - 전역 `pnpm` 명령이 없어 루트 스크립트의 하위 명령 실행이 실패했다. `corepack pnpm`으로 실행하도록 수정했다.
