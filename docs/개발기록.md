## 기록 방법

이 문서는 **왜 요청했고, 무엇을 고민했으며, 어떻게 바뀌었는지**를 기록한다. 기능 요구사항은 기능명세서, 단계별 완료 여부는 개발계획, 설치·실행 명령은 README에서 관리한다.

새 요청이나 결정이 생기면 날짜와 기록 번호를 붙여 아래에 추가한다. 기존 결정을 바꾸는 경우 이전 기록을 지우지 않고 변경한 이유와 대체하는 기록 번호를 남긴다. 실제로 사용자가 말한 내용과 구현 과정에서 개발자가 검토한 내용을 구분한다. 확인되지 않은 의도나 고민을 사용자 발언으로 기록하지 않는다.

API 키, 인증 토큰, 개인정보는 기록하지 않는다. 연결 검증은 설정 예제 확인, 테스트용 응답 검증, 실제 API 호출 성공을 구분한다.

## 초기 세팅 설명

### 현재 개발 상태

2026-10-22 기준으로 1단계의 프로젝트 기반과 로컬 저장 흐름을 구현했다. 게임 선택부터 질문 저장, 테스트 응답 표시, 새로고침 후 대화 복원까지 실행할 수 있다. **`gpt-6.1-sol` 채팅과 `text-embedding-3-large` 임베딩의 실제 연결까지 검증하여 1단계를 완료했다.** 상세 경과는 기록 009~010을 참고한다.

현재 데이터는 저장 기능을 확인하는 가상 게임 1개와 테스트 판본이다. 공식 규칙을 확보한 게임은 아니며 실제 보드게임 규칙을 판정하지 않는다. 초기 검증 후보 3개 게임과 최종 목표 100개 이상 게임 지원은 이후 데이터 확보 단계의 범위다.

### 기술 구성과 역할

| 구성 | 역할 | 현재 상태 |
|---|---|---|
| Next.js App Router + TypeScript | 게임 선택·대화 화면과 API 호출 | 기본 화면 구현, Next.js 16.4.2 빌드 검증 |
| Python + FastAPI | 입력 검증, 대화·요청 처리, 저장·조회 API | 구현 |
| SQLite | 게임·문서·대화·요청의 영속 저장 | 로컬 `data/app.db` 사용 |
| SQLAlchemy | Python 객체와 DB 테이블 연결, 트랜잭션 처리 | 모델·제약조건 구현 |
| Alembic | DB 스키마 변경 이력을 코드로 관리 | 초기 마이그레이션 구현·검증 |
| 채팅 연결부 | 모델 제공업체 요청·응답 처리 | mock 및 GMS 예제 규격의 호환 연결부 구현 |
| 임베딩 연결부 | 검색용 벡터 생성과 차원 검증 | GMS `text-embedding-3-large` 실제 호출·3,072차원 확인 |
| ChromaDB | 게임 메타데이터·규칙 청크의 벡터 검색 | 후속 구현 예정, 저장 경로만 준비 |
| LangGraph | `retrieve → generate` RAG 흐름 | 후속 구현 예정 |
| pnpm / uv | 프론트엔드 / 백엔드 의존성 관리 | 잠금 파일 포함 |

기존 계획에 따라 Windows에서 Docker 없이 실행한다. 공개 배포, Neon, Chroma Cloud는 현재 범위에 포함하지 않는다. 로컬 실행을 기준으로 하지만 향후 실제 모델 호출과 문서 수집에는 인터넷 연결이 필요하다.

### 화면과 API가 연결되는 방식

웹 개발 서버는 `127.0.0.1:3000`, FastAPI는 `127.0.0.1:8000`에서 실행한다. 브라우저는 웹 서버의 `/api/v1` 주소로 요청하고, Next.js가 해당 요청을 FastAPI로 전달한다. API 문서는 `http://127.0.0.1:8000/docs`에서 확인한다.

현재 질문 처리 흐름은 다음과 같다.

1. 샘플 게임을 선택하면 선택 게임·판본과 익명 세션을 연결한 대화를 생성한다.
2. 질문을 보내면 사용자 메시지와 요청 상태를 SQLite에 저장한다.
3. API는 `202 Accepted`와 요청 ID를 반환한다.
4. 백그라운드 작업이 테스트 응답을 생성하고 응답 메시지와 완료 상태를 저장한다.
5. 웹은 요청 상태를 조회해 완료된 대화를 표시한다.
6. 새로고침하면 브라우저에 보관한 대화 ID와 세션 쿠키를 이용해 SQLite의 대화를 다시 불러온다.

대화 본문은 DB에 저장한다. 브라우저의 localStorage에는 최근 대화 ID를 저장하며, 이것만으로 대화 접근 권한을 부여하지 않는다. 서버에서 세션 쿠키와 대화 소유 세션을 비교하고 다른 세션의 접근을 차단한다.

현재 UI는 샘플 게임의 첫 판본을 사용한다. 전체 판본·확장 선택, 게임별 대화 전환, 실제 인용 근거 패널은 후속 화면 구현 범위다.

### DB와 요청 처리에서 미리 준비한 부분

게임, 판본, 확장, 문서, 문서 적용 범위, 수집 상태, 대화, 메시지, 인용, 요청을 저장하는 10종의 엔터티와 다대다 관계용 연결 테이블 2개를 만들었다.

| 준비한 사항 | 필요한 이유 |
|---|---|
| 게임·판본 일치와 확장 호환 제약 | 다른 게임이나 호환되지 않는 판본의 데이터 연결 방지 |
| 문서와 적용 범위 분리 | 하나의 원문을 여러 게임·판본 범위에 연결 |
| 인용 제목·버전·페이지 등의 스냅샷 | 원문 정보 변경 후에도 과거 답변의 인용 정보 보존 |
| 대화별 `client_request_id` 중복 방지 | 같은 요청 재전송 시 메시지와 작업이 중복 생성되는 문제 방지 |
| 대화당 진행 중 요청 1개 제한 | 같은 대화에서 여러 생성 작업이 겹치는 문제 방지 |
| 시작 시 미완료 요청을 실패로 복구 | 서버 종료로 중단된 요청이 계속 처리 중으로 남는 문제 방지 |
| 외래키 검사·WAL·쓰기 대기 시간 설정 | SQLite 데이터 무결성과 로컬 읽기·쓰기 처리 지원 |

DB는 애플리케이션 실행 시 임의로 테이블을 만드는 방식 대신 `alembic upgrade head`로 준비한다. API는 단일 프로세스로 실행하며, 연결부 응답을 기다리는 동안 DB 트랜잭션을 유지하지 않도록 구성했다.

### 모델과 임베딩 설정

사용자 안내에 따라 `../streamlit_lab/step6_context.py`에서 다음 예제를 확인했다.

| 항목 | 확인한 내용 |
|---|---|
| 제공 경로 | GMS |
| API 기본 주소 | `https://gms.ssafy.io/gmsapi/api.openai.com/v1/` |
| 예제 모델 ID | `gpt-5.4-nano` |
| 인증 설정 | `GMS_KEY`를 API 키로 전달 |
| 호출 형태 | `chat/completions` 호환, `model`과 역할별 `messages` 전달 |

기존 계획의 `5.6 Sol` 표시 이름과 예제의 실제 모델 ID가 동일하다고 판단하지 않았다. 현재 기본 모델 ID는 확인 가능한 예제 값을 사용했으며 실제 호출 성공을 뜻하지 않는다.

채팅과 임베딩은 주소·키·모델을 각각 설정할 수 있게 분리했다. 채팅 모델이 응답한다고 해서 임베딩 지원까지 확인된 것으로 처리하지 않기 위해서다. 임베딩 응답은 개수, 인덱스, 숫자 유효성, 차원을 별도로 검사한다.

기본 설정은 두 연결 모두 `mock`이다. mock 채팅은 규칙 판정 불가를 명시한 테스트 문구를 반환한다. mock 임베딩의 8차원 벡터는 연결 구조를 확인하는 테스트 데이터이며 의미 검색용 모델 결과가 아니다.

`probe --live`는 mock 결과를 실제 연결 성공으로 인정하지 않는다. 초기에는 두 연결 모두 `not_verified`였으며, 현재 로컬 설정에서는 채팅과 임베딩 모두 `live_ok`를 확인했다. 실제 호출은 probe에서 검증했고, 웹 질문 흐름은 공식 규칙 검색을 연결하기 전까지 mock 전용이다.

설정 방법과 실행 명령은 [README의 실제 연결 검증 안내](../README.md#설정과-실제-연결-검증)를 따른다.

- 검증: 실제 질문 5/5 예상 동작 부합, 로컬 원문 추출·청크 대조, 평가 도구 Ruff 통과. 애플리케이션 코드는 변경하지 않았고 기존 41개 자동 테스트는 재실행하지 않았다.
- 완료 판단: 3단계 초기 완료 기준 충족. 전체 110게임의 품질·출처 인증을 뜻하지 않는다. 다음은 4단계 화면·API 통합이다. [상세 결과](../reports/stage3-progress.md).

### 기록 — 모노레포 구조 평가와 계약·CI 정비

- 날짜: 2026-10-22
- 사용자 요청: 현재 모노레포 구조를 평가하고, 이어서 개선 사항을 수정한다.

- 결정: 위 세 가지를 우선 수정했다. 평가에서 제안했던 루트 스크립트의 중첩 `corepack pnpm` 제거는 확인 결과 Corepack 전역 활성화 없이는 스크립트 안에서 `pnpm`을 찾지 못해 철회했다. `reports/`·`evals/` 정리는 파일 이동이 필요해 보류했다.
- 수정:
  - 계약: `export-openapi`가 실행 위치와 관계없이 `apps/api/openapi.json`에 쓴다. 루트 `sync:api`(내보내기+타입 생성)와 `check:api`(동기화 후 변경 시 실패)를 추가했다. pytest `test_committed_openapi_is_current`가 커밋된 스키마 누락을 검출한다.
  - CI: `.github/workflows/ci.yml` 추가. api(ruff·alembic·pytest), web(생성 타입 일치·typecheck·lint·format·build), e2e(앞 두 작업 통과 후, 실패 시 결과 업로드). 구버전 Corepack 서명 키 오류를 피하려고 CI에서 Corepack을 갱신한다.
  - Playwright: API 서버를 `uv run --project apps/api`로 실행하고, 로컬은 Edge·CI는 Chromium을 사용한다.
- 검증: 생성 타입이 현재 `openapi.json`과 일치함을 확인했다. Playwright 설정 로드(`--list`)와 TypeScript 검사 통과. 로컬 셸에 `uv`가 없어 pytest·신규 테스트·E2E는 실행하지 못했고 CI 워크플로도 아직 실제로 돌리지 않았다.
- 남은 사항: 커밋된 `openapi.json`이 현재 백엔드와 다르면 신규 테스트가 실패하며 `corepack pnpm sync:api`로 갱신한다. 이 PC는 `core.autocrlf=true`라 로컬 `format:check`가 CRLF 때문에 실패하므로 `.gitattributes`의 `eol=lf` 지정을 검토한다. 로컬 Node 20.17의 Corepack은 `npm i -g corepack@latest`로 갱신이 필요하다.

### 기록 — 5단계 검색 고도화와 100개 게임 지원 점검

- 날짜: 2026-10-23
- 사용자 요청: 개발계획 단계 5 진행, 개발 기록을 이 문서에 남김.
- 구현:
  - 검색: `rule_u/search.py` 추가. 같은 게임·판본·문서 필터의 청크에 BM25 키워드 검색(어절+음절 2-gram)과 벡터 검색을 적용하고 RRF(k=60)로 병합한다. MMR(λ=0.5)은 비교 모드다. 기존에 정의만 있던 `SEARCH_MODE` 설정을 `retrieve`에 연결했고 기본값 `similarity`를 유지했다.
  - FAQ·정오표: `type=faq|errata` 문서는 `config/document-relations.json`의 검증된 관계(같은 판본, 같은 범위의 규칙서 수정)가 있을 때만 검색에 포함한다. 프롬프트에는 수정 관계와 우선 적용 규칙을 추가했다. 현재 카탈로그 117문서는 모두 규칙서라 결합 0건이고 관계 파일은 빈 상태다.
  - 지원 점검: `rule_u/stage5.py`의 `compare`·`audit` 명령. 판본별로 문서·추출·판독 가능 여부·판본 연결·색인 청크 수·근거 확인 질문을 확인한다. `--apply`일 때만 `editions.supported`를 기록한다.
  - 질문: 판독 가능 111판본 전체에 근거 확인 질문 116문항(2단계 8 + 신규 108)을 두었다. 핵심 4게임에는 예외·정보 부족·근거 없음 질문 12문항을 추가했다.
- 발견한 문제: 2단계에서 추출 성공으로 집계된 문서 중 6건이 글꼴 매핑 오류로 깨진 문자이거나 숫자표뿐이었다(카멜 업 2, 금지된 섬 보드라이프판, 가지각새, 러브레터, 여섯불꽃). 기존 20자 기준만으로는 걸러지지 않아 판독 가능성 검사를 추가했다. 다국어·카드 라벨 페이지는 문서 실패로 보지 않는다. 복구는 하지 않았다.
- 검토·결정 (개발 과정의 판단):
  - 116문항에서는 hybrid가 우세했다(Hit@5 1.000, MRR 0.843 vs similarity 0.966, 0.779). 독립 질문 8개에서는 similarity가 우세했다(MRR 0.781 vs 0.708). 신규 질문을 청크를 보고 작성해 키워드 편향을 배제할 수 없다. 따라서 기본값 전환을 보류하고, 계획대로 기본 검색을 유지해 전후 비교가 가능하게 했다.
  - 정답 라벨 보완은 한 방식이라도 놓친 문항에 한해 같은 규칙이 적힌 다른 페이지를 문구 검색으로 찾아 4문항에 추가했다. 모든 방식에 동일하게 적용된다.
  - 지원 판정은 현재 기본 검색 기준으로 보수적으로 기록했다. hybrid 기준이면 검색 실패 4게임도 통과한다.
- 실제 외부 호출: 신규 질문 108개의 임베딩을 GMS로 전송했다(질문 문장만, 규칙 본문 없음). 핵심 게임 답변 평가는 근거 청크와 질문을 GMS 채팅으로 보낸다는 질문에 사용자가 "전송 승인"을 선택한 뒤 24회(2방식×12문항) 실행했다. BGG 조회는 껐다. 키는 출력하지 않았다.
- 결과:
  - 지원 102게임·107판본. 로컬 DB에 적용했다(이전에는 모든 판본이 미지원). 미지원은 깨진 문자 4게임과 기본 검색 근거 확인 실패 4게임(숲의 속삭임, 르 아브르, 포션 폭발, 갤러리스트)이다.
